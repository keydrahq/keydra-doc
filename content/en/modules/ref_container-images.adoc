= The published images

{product-name} is published at `{image-registry}` as three images. Which one you want depends
on whether the interface is served by {product-name} or by something else.

[cols="2,3",options="header"]
|===
| Image | What it is

| `{image-standalone}`
| The interface built into the API's own static resources, so one container serves both. This
is the ordinary deployment and the one the manifests in the repository use.

| `{image-backend}`
| The API alone. For a deployment that serves the interface separately — from a CDN, from an
existing web server, or as its own pod.

| `{image-ui}`
| The interface, and the proxy it needs. The image carries nginx: it serves the static files
and routes `{api-base}` and `/graphql` to whatever `KEYDRA_BACKEND` names, WebSocket upgrades
included. So a split deployment does not need a reverse proxy in front of both — this is that
proxy.
|===

.The interface and the API must share an origin
[IMPORTANT]
====
The interface calls `{api-base}` and `/graphql` as relative paths. There is no setting that
points it at an API somewhere else, deliberately: an absolute API address in a static bundle
is a build-time decision about a run-time fact, and it is also a cross-origin cookie problem.

So the interface and the API have to answer on one address. `{image-ui}` is built to be that
address: it serves the interface at `/` and forwards `{api-base}` and `/graphql` — and the
WebSocket upgrades on them — to `KEYDRA_BACKEND`. The session cookie stays a first-party
cookie, which is what makes `SameSite=Lax` work.

Put your own proxy in front of it if you already have one, but do not put one *between* the
two: the routing is already done.

If you have no reason to run them apart, use `{image-standalone}`.
====

.Tags
[NOTE]
====
The examples here use `{image-tag}`. A deployment should pin a version instead, so a restart
does not become an upgrade nobody scheduled.
====
